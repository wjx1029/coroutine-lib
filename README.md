# coroutine-lib
在 Linux 平台上使用 C++ 实现了部分高性能服务器框架，其核心是一个自定义协程库。该协程库基于 ucontext_t 实现轻量级的上下文切换与协同调度，并与 epoll 事件机制及定时器系统深度集成，能够高效、灵活地处理异步 I/O 事件和定时事件的回调。

---

## 模块说明

- thread：这个模块主要为了弥补协程的缺点，通过多线程 + 多协程的方式，更好地利用多核 CPU 资源。

- fiber：负责协程的创建、暂停、恢复等核心逻辑，是真正运行任务的单元。

- scheduler：如果没有这个类，就需要用户手动控制协程的执行与切换，不够灵活也不够智能。

- ioscheduler：即 IO 调度器，是 scheduler 的 IO 增强版。协程库要用于实际服务器项目，必须能处理文件描述符（fd）。该类使用 epoll 监听 fd 上的读写事件，事件触发后将协程加入调度器等待执行。

- timer：服务器通常需要定时器处理定时任务。该模块负责定时器的创建、添加与删除，内部使用最小堆管理超时时间；定时器触发时通过 tickle 信号唤醒 ioscheduler 中的 epoll_wait。
  
- hook：只有结合 hook 与 ioscheduler，才能真正实现非阻塞的服务器框架。虽然前面已经实现了协程调度，但如果不修改系统调用行为，就无法在阻塞时自动挂起 / 恢复协程。例如 sleep(1) 仍然会阻塞整个线程，无法体现协程优势。因此通过 hook 替换原始系统调用，增强其逻辑：将 sleep(1) 这类操作转为定时任务，放入 timer 的最小堆中等待超时，之后唤醒 epoll，再将协程交回调度器执行。

## Thread 类
Thread类在协程库中主要用于创建并管理底层线程，为协程提供运行环境，同时通过线程局部存储和同步机制，为协程调度提供必要支持。它确保协程可以在合适的线程上被正确的调度和执行
- Thread 类的构造函数接收两个核心参数：
    - std::function<void()> m_cb：线程要执行的任务函数
    - m_name: 线程名称成员变量
  
- 通过 pthread_create() 将 run 函数绑定为线程入口函数。run 方法主要负责两件事：
    - 完成线程自身的初始化工作
    - 调用线程真正要执行的任务（函数对象 cb）
    - 实现中使用了 Semaphore 信号量来控制线程初始化的同步，确保所有线程都能正确初始化，避免出现未初始化完成就运行的问题。
  
- 对 Thread 类构造函数中 std::function 的分析：线程构造函数里有一个关键知识点：std::function<void()> cb。它是 C++ 标准库中的通用可调用对象封装，用来存放返回值为 void、无参数的函数或可调用对象。你可以把它理解成一个函数容器，类似 vector 这种容器。
为什么线程需要这个 function？因为线程是 CPU 调度的基本单位，线程必须有执行主体。如果没有要执行的函数，那线程本身就没有存在的意义

- 其余方法说明：
    - GetThreadId()：通过系统调用获取真实的线程 ID
    - 注意：线程 ID 与 getpid() 返回的进程 ID不同
    - 其他函数主要是获取 / 设置线程名称、获取线程 ID 等常规操作

- static thread_local 是什么意思?
    - static 表示变量的生命周期持续到程序结束时才销毁。
    - thread_local 表示变量是线程局部的，即每个访问该变量的线程都会拥有一个独立副本。例如每个线程都会独立拥有一个 Thread 指针和当前线程名称，多个线程的副本互不干扰。

## Fiber 类
Fiber类提供了协程的基本功能，包括创建、管理、切换和销毁协程。它使用了ucontext_t结构(主要使用非对称协程)保存和恢复协程的上下文，并通过std::function来存储协程的执行逻辑。
- 协程的状态
    - 设置三种协程的状态：就绪态、运行态和结束态
    - 一个协程要么正在运行(RUNNING)，要么准备(READY)，要运行结束(TERM)。
- 生命周期管理
协程没有专门的“停止”指令。当绑定的执行函数运行结束时，协程即告终止。此时，系统会自动触发一次上下文切换，将控制权返回给关联的调度上下文（即主协程或调度器）
- 底层实现（有栈协程）：
协程可被视为一个支持中间状态切换的函数。在实现上，需为每个协程绑定入口函数。此外，由于本项目采用的是独立栈（有栈协程）方案，在初始化阶段必须为每个协程实例分配专属的栈空间，用以保存该协程在切换时的局部变量和调用链状态
- 构造函数:
    - **子协程构造（带参）：** 采用有栈协程设计，负责分配独立栈空间，并将入口函数封装进 ucontext_t。通过 bool use_caller 参数决定该协程是切回调度协程还是主协程。
    - **主协程构造（私有无参）：** 仅由 GetThis() 内部调用。它不分配栈空间，而是通过 getcontext 捕获当前线程的执行环境。它是协程切换的“锚点”。
- 析构函数:
    - **资源回收：** 析构函数会原子递减全局活跃协程计数。对于有栈的子协程，必须通过 assert 确保其已处于结束（TERM）或异常（EXCEPT）状态，随后释放栈空间。
    - **主协程特殊性：** 主协程由于使用线程原始栈，其 m_stack 为空，析构时不执行 delete 操作。在实现中需要确保：当主协程析构时，当前线程不应再有任何待处理的子协程，否则会导致上下文丢失。
### 协程切换的实现：Resume 与 Yield
在非对称协程架构中，子协程永远知道它的“归宿”是谁。切换逻辑由 m_runInScheduler 标志位分为两种模式：
1. 调度器模式 (m_runInScheduler == true)：
   - Resume： 调用 SetThis(this) 后，通过 swapcontext 将当前调度协程的上下文保存，并切换到子协程。

   - Yield： 子协程挂起时，调用 SetThis(t_scheduler_fiber)，将当前上下文保存到子协程对象，并切回调度协程。

   - 意义： 这种模式用于高性能的任务分发，子协程挂起后，调度器可以立刻安排下一个任务。
2. 手动模式 (m_runInScheduler == false)：

    - Resume： 直接与线程的主协程交互。保存主协程上下文，切换至子协程。

    - Yield： 子协程挂起，切回主协程。

    - 意义： 常用于简单的逻辑跳转或单元测试，不涉及复杂的任务调度算法。    
### Reset
**主要目的是:**重用一个已经终止的协程对象，从而避免频繁创建和销毁对象带来的开销。通过重置协程的状态和任务，可以在执行新的任务时重新利用这个协程对象。
### 协程入口函数
为了实现协程结束后自动返回调度器的闭环，封装了 MainFunc。

- 流程： 协程启动后首先GetThis()获取当前协程的指针（shared_ptr）。接着执行业务回调 m_cb。任务完成后，强制将状态置为 TERM。

- 核心细节： 最后必须使用原始指针而非智能指针。因为 shared_ptr 会在协程栈上增加引用计数，导致即使协程执行完毕，其引用计数也无法归零，从而引发内存泄漏。使用 raw_ptr 确保了协程能够被调度器正常回收。

- 收尾： 最后调用 yield()。此时由于状态已是 TERM，协程将最后一次交出 CPU 执行权，回到调度器进行资源清理。
### GetThis
- 返回一个正在运行的协程t_fiber
- 若没有这个协程, 则调用*Fiber()*创建主协程, 并返回主协程
- 若没有主动设置, 调度协程默认为主协程

## Scheduler 类
### 调度器设计的核心思路
- 首先，Scheduler 是围绕“多线程”与“多协程”的深度整合而设计的。引入调度器的目的在于构建一个自动化的任务执行环境。
  
- 相比于单一使用 Fiber 类时需要用户手动调用 resume 和 yield 来切换状态，Scheduler 实现了调度的自动化与智能化——正如那句话所说，依靠自动化机制（“机器办事”）比依靠复杂的手动管理（“不靠谱的人”）更加稳健高效。
  
- 调度器（Scheduler）的出现，把程序员从繁琐的上下文切换中解放了出来。它让‘调度协程’充当了全职管家，没事时管家在后台待命，有活时管家就把执行权交给‘子协程’，任务完成后子协程自动交还执行权，从而实现了任务的自动化批量消耗。
  
- 调度器的核心逻辑在于：通过维护一个线程池，协调多个线程并发地从任务队列中提取任务，并交由协程去执行。 这种“多线程提取、多协程运行”的 M:N 调度模型，正是 Scheduler 类设计的灵魂所在。
### 协程调度器的相关核心概念
#### 调度器任务的定义：
- 对于协程调度器而言，协程是原生的调度单位。
- 函数同样可以作为调度任务。原因在于：协程本质上是函数及其运行状态（上下文）的组合。将函数视为任务，可以简化用户的使用逻辑。在实际实现中，调度器内部会将传入的函数包装成协程后再进行调度，但对外部接口而言，调度器应同时支持协程和函数。
#### 多线程调度：
- 基于协程的基本特性，一个线程在同一时刻只能运行一个协程。为了提升调度器的吞吐量和并发能力，引入多线程调度机制。通过维护一个线程池，实现多个线程同时运行多个协程，这种M:N的调度模型（M个协程运行在N个线程上）在处理高并发IO时效率远高于单线程。
#### 问题：是否可以将调度器所在的线程（Caller线程）纳入调度范围？
- 答案是肯定的。在main函数（或其他线程）中创建调度器时，如果不将该线程纳入调度，则该线程在启动调度器后通常只能处于阻塞等待状态。
- 将Caller线程作为调度线程之一，不仅可以充分利用现有线程资源，减少额外创建线程的开销，还能让主协程直接参与任务分发与执行，从而提高整体运行效率。
#### 调度器的运行机制：
- 调度器实例化后，内部会初始化一个线程池。启动调度后，所有调度线程会循环从任务队列中获取任务并执行。
- 调度线程的数量决定了并行执行任务的能力。当任务队列为空时，调度线程不应退出，而是进入等待（或执行Idle协程）状态，直到有新任务进入队列。
#### 添加调度任务：
- 添加任务的本质是将任务对象（协程或函数）推入调度器的任务队列。
- 仅靠添加任务是不够的，还需要配套的通知机制（Tickle）。因为调度线程在无任务时可能处于挂起或阻塞状态，添加任务后必须通过某种方式（如信号量、管道写入或条件变量）唤醒调度线程，以确保新任务能够被及时处理，避免不必要的轮询导致的CPU高占用。
#### 调度器的停止：
- 调度器必须具备优雅停止的能力，以便回收线程资源。只有当任务队列已清空，且所有调度线程都已完成当前任务并安全退出后，调度器才算真正停止。
#### 总结：
调度器内部维护一个任务队列和一个调度线程池。启动调度后，线程池按序从队列中取出任务执行。调度线程池可灵活包含Caller线程。当所有任务执行完毕且无新任务时，线程池进入空闲状态。一旦新任务到达，通过通知机制唤醒线程池重新开始调度。执行停止逻辑时，各调度线程依次退出，最终完成调度器的资源释放。
### 调度时的协程切换问题：
1. 当主线程（Caller线程）不参与调度时 (use_caller = false)：
在这种模式下，调度器会创建专门的调度线程池，而创建调度器的线程（通常是main函数所在的主线程）不参与执行任务。主线程的角色仅限于向调度器添加任务、发起停止指令，并调用stop()方法等待所有调度线程执行完毕后退出。
   - 切换机制： 每一个新创建的调度线程都会运行一个入口函数（调度协程，即run方法）。在调度线程内部，上下文切换发生在调度协程与**任务协程（子协程）**之间。主线程及其主协程不参与此过程。
   - 状态判断： 调度线程会根据调度器的运行状态（如m_stopping）判断是否继续从任务队列中取任务。此时，新线程的“调度协程”充当了管理者的角色，负责拉起（swapIn）任务协程，并在任务完成后切回（swapOut）调度协程。
2. 当主线程（Caller线程）参与调度时 (use_caller = true)：
在此模式下，调度器不仅会根据配置创建新线程，还会将创建调度器的线程（Caller线程）也纳入调度范围。这意味着Caller线程不再只是“旁观者”，它也会执行任务。
    - 多线程情况： 其他新创建的任务线程切换逻辑与上述一致。而Caller线程除了负责初始化，还会显式地调用调度器的run方法，使其身份从“普通线程”转变为“调度线程”。

    - 单线程情况： 如果设置线程数为1且use_caller为true，调度器将不再创建新线程。所有的协程任务都在Caller线程内完成。此时，该线程既负责任务分配，也负责任务执行和调度器停止。
### 在单线程环境下，若主线程参与调度，线程内会存在三类协程：

- 主协程 (Main Fiber)：对应main函数所在的执行上下文。

- 调度协程 (Scheduler Fiber)：运行调度器run方法的协程，负责任务分发。

- 任务协程 (Task Fiber)：待执行的业务逻辑函数或协程。
### 运行顺序逻辑（极其重要）：

- 主协程运行，创建调度器。

- 主协程向调度器添加任务。

- 启动调度：主协程通过调用stop()或手动切入调度循环，让出执行权给调度协程。调度协程开始从任务队列按顺序获取任务。

- 任务切换：调度协程取出任务后，切入（swapIn）该任务协程。任务执行结束后，必须切回（swapOut）调度协程，以便继续调度下一个任务。

- 调度结束：所有任务执行完毕且满足停止条件后，调度协程让出执行权，切回主协程，保证程序正常结束。
### 核心设计：三层协程切换逻辑
为了解决“调度协程与子协程频繁切换导致主协程‘跑飞’（上下文丢失）”的问题，引入了线程局部变量来保存不同身份的协程上下文：

- 成员变量 m_runInScheduler：用于标记该协程是否受调度器管理。

- 身份识别：
    - 任务协程：m_runInScheduler = true。

    - 主协程与调度协程：m_runInScheduler = false。

- resume（唤醒）逻辑：

    - 若 m_runInScheduler 为 true，则与该线程的调度协程（t_scheduler_fiber）进行上下文切换。

    - 若 m_runInScheduler 为 false，则与该线程的主协程（t_thread_fiber）进行切换（脱离调度器使用）。

- yield（让出）逻辑：

    - 同理，根据标志位决定切回调度协程还是主协程。
